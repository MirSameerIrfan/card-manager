# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal finance tracker for bills, credit cards and loans. The repo and package are named `card-manager`; the product name shown in the UI, emails and README is **MoneyScope**.

Stack: React 19, TanStack Start (file-based router + server functions) on Nitro, Vite 7, Tailwind CSS 4, Prisma 7 on PostgreSQL, better-auth, Sentry. Deployed to Netlify.

## Commands

```bash
npm run db:start # start the local Postgres (npx prisma dev, background); db:stop stops it
npm run dev      # dev server on http://localhost:3000
npm run build    # vite build into .output
npm run start    # run the built server from .output
npm run test     # vitest run
npm run lint     # eslint (type-aware, uses tsconfig.json)

npx vitest run src/components/dashboard/dashboard-utils.test.ts   # one file
npx vitest run -t "name of test"                                  # one test by name

npx prisma generate      # REQUIRED after install and after schema changes
npx prisma migrate dev   # create/apply a migration locally
npm run seed             # (re)create demo@example.com / password1234 in the local database
npm run db:migrate:prod  # apply pending migrations to production (Supabase), using .env.production
```

`npm run build` does not type-check. Run `npx tsc --noEmit` for that; it should report no errors. Before committing, run `npm run test`, `npm run lint` and `npm run build`.

### First-time setup

The Prisma client is generated into `generated/prisma/` (gitignored) and imported from there by `src/lib/prisma.ts`. A fresh clone will not build or run until `npx prisma generate` has been run.

There are two environments, each with its own database:

- **Local**: `.env` (gitignored) points at a Postgres on this machine, started by `npm run db:start` (`npx prisma dev --name card-manager` on fixed ports 51213–51215). New setup: `cp .env.example .env`, set `BETTER_AUTH_SECRET`, `npm run db:start`, `npx prisma migrate dev`, `npm run seed`.
- **Production**: Netlify, against the Supabase project. Its settings are Netlify environment variables. The only production values on disk are the Supabase URLs in `.env.production` (gitignored), read only by `npm run db:migrate:prod`. Migrations reach production only through that command; nothing applies them on deploy.

Keep `.env` pointed at the local database. `prisma.config.ts` prefers `DIRECT_URL` over `DATABASE_URL`, so a Supabase `DIRECT_URL` left in `.env` sends every local migrate to production. `prisma/seed.ts` refuses any non-local host because it deletes users.

| Variable | Used for |
| --- | --- |
| `DATABASE_URL` | Runtime Postgres connection. Locally the `prisma dev` server; in production the Supabase transaction pooler (port 6543). Required. |
| `SHADOW_DATABASE_URL` | Local only: the empty database `prisma migrate dev` diffs against (the `prisma dev` shadow port). Without it `migrate dev` fails. |
| `DIRECT_URL` | `.env.production` only: the Supabase session pooler (port 5432), used by `prisma migrate` in preference to `DATABASE_URL`. |
| `DATABASE_POOL_MAX`, `DATABASE_POOL_IDLE_TIMEOUT_MS`, `DATABASE_POOL_CONNECTION_TIMEOUT_MS` | Per-instance pg pool limits (defaults 5 / 10000 / 10000). |
| `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET` | App base URL and signing secret. Both required in production; the URL defaults to `http://localhost:3000`. |
| `RESEND_API_KEY`, `RESEND_FROM_EMAIL` | Auth emails. Without the key, verification and password reset links are logged to the server console instead — this is how you complete those flows locally. |
| `SENTRY_DSN`, `VITE_SENTRY_DSN`, `SENTRY_AUTH_TOKEN` | Server, client, and build-time Sentry. Optional; Sentry is a no-op without a DSN. |

The production database is Supabase-hosted Postgres accessed through the Prisma ORM (no Supabase client or Supabase Auth): project `card-manager` (ref `phnxlkpdwfldhhyatohp`, region us-east-2, free plan), where the app connects as the dedicated role `card_manager_app`, which owns the tables, through the pooler host `aws-0-us-east-2.pooler.supabase.com`.

The built server does not load `.env` by itself. To run a production build locally against the local database: `NODE_ENV=production node --env-file=.env .output/server/index.mjs`.

## Architecture

### Request flow

- `src/routes/` is the file-based route tree. `src/routeTree.gen.ts` is generated by the router plugin — never edit it; it regenerates when the dev server or build runs.
- Route files are thin: they declare `beforeLoad` guards, `loader`, search-param validation (zod), and point `component` at a page component in `src/components/<area>/`.
- All data access goes through **server functions** (`createServerFn`), called directly from loaders and components. There are no REST endpoints except the better-auth catch-all at `src/routes/api/auth/$.ts`.
- After any mutation, components call `router.invalidate()` to re-run loaders. There is no TanStack Query cache or client store; loader data is the source of truth (`getRouteApi("/dashboard").useLoaderData()`).
- `src/server.ts` and `src/start.ts` wrap the server entry and all requests/server functions in Sentry middleware. `src/server.ts` imports `instrument.server.mjs` (the server `Sentry.init`) as its first import; that is how Sentry starts in every environment, since Netlify cannot start Node with `--import`. `src/server.ts` also adds `X-Frame-Options: DENY` and `frame-ancestors 'none'` to every response so other sites can't frame the app.

### Where server functions live

- `src/utils/auth.functions.ts` — session lookup, sign out, profile name change.
- Anything that checks a password or sends an email (sign up, sign in, resend verification, change email, change password, forgot/reset password) does not use a server function: the pages call `authClient` so the request goes through `/api/auth/*`, where better-auth's rate limiter applies (it does not apply to `auth.api.*` calls). Don't add a server function that wraps one of these: server function ids are a SHA-256 of the file path and export name, so anyone can call one even if no page imports it. `getAuthErrorMessage` in `src/utils/auth-errors.ts` maps `authClient` errors to UI messages.
- `src/components/dashboard/dashboard.functions.ts` — dashboard read plus add/update/delete payment, colocated with the dashboard components.

### Auth

- `src/lib/auth.ts` is the better-auth server instance (Prisma adapter, email/password, **email verification required**). `tanstackStartCookies()` must stay the last plugin.
- `src/lib/auth-client.ts` is the browser client (`useSession`, `signOut`), used by `Header` and the profile page for reactive session state.
- Server functions call `auth.api.*` and must forward the incoming request headers (`getRequest()` → headers object) so the session cookie is read and set.
- A session alone is not enough: every protected path checks `session.user.emailVerified === true`. This is enforced twice — in the route's `beforeLoad` (redirect to `/auth/login`) and again inside each server function (throws `Unauthorized`). New protected routes and server functions need both.
- `redirectIfAuthenticated()` in `src/utils/route-guards.ts` is the guard for guest-only routes (`/`, `/auth/login`, `/auth/signup`); it deliberately swallows session-lookup errors and re-throws redirects.
- Password reset: `/auth/forgot-password` → emailed link → better-auth validates it at `/api/auth/reset-password/:token` and redirects to `/auth/reset-password` with `?token=` or `?error=`. Resetting revokes all of the user's sessions.
- Rate limiting is better-auth's built-in limiter, with counters in the `rateLimit` table. It is turned on by `isProduction` in `src/lib/auth.ts`, which the build fixes in place; better-auth's own default checks `NODE_ENV` at runtime, which Netlify functions don't have, so leaving it to the default turns it off in production. It is keyed by `x-nf-client-connection-ip`, the IP Netlify saw, not `X-Forwarded-For`, which the client sets. Requests without that header (a local production build) share one bucket per path.
- Auth emails are sent after the response (`advanced.backgroundTasks`, handed to Netlify's `waitUntil`), so response time doesn't reveal whether an email has an account. Emails don't include the user's name: anyone can sign up with someone else's address and a name of their choosing.
- `/auth/verify-email` handles three cases (error param, token param, or bare redirect after better-auth verified server-side); see the comments in that route before changing the flow.

### Data model

`prisma/schema.prisma` has the better-auth tables (`User`, `Session`, `Account`, `Verification`, `RateLimit`, mapped to better-auth's table names) plus three payment tables with snake_case model names: `credit_card`, `loan`, `recurring_bill`, each owned by `userId`.

- The three payment types have different column names for the same concept (`amountDue`/`monthlyPayment`/`amount`, `dueDate`/`nextPayment`/`dueDate`). The server functions and `Dashboard.tsx` branch on a `type: "credit_card" | "loan" | "recurring_bill"` discriminator and map to a common shape; a new field usually has to be threaded through all three branches in add, update, and the dashboard mapping.
- `updatedAt` on the payment tables has no `@updatedAt`, so writes must set it explicitly.
- Updates verify ownership with a `findUnique` + `userId` comparison before writing; keep that check on any new mutation.
- `src/lib/prisma.ts` owns a single pg `Pool` and `PrismaClient`, cached on `globalThis` so dev HMR does not leak pools. Import `prisma` from there; never construct another client. `GET /api/health` reports pool usage.
- Every table has row level security enabled with no policies, so only the owning role (the app) can read it; Supabase's Data API roles cannot. A migration that adds a table must also enable RLS on it.
- `npm run seed` (`prisma db seed`; the command is `migrations.seed` in `prisma.config.ts`, run with tsx) runs `prisma/seed.ts` against the local `DATABASE_URL` (it refuses other hosts). It deletes and recreates the demo user **demo@example.com / password1234**, already email-verified, with sample credit cards, loans and recurring bills whose due dates are relative to today (one overdue, the rest due soon or auto-pay). Re-run it to reset the demo data and refresh the dates. Prisma 7's `migrate dev` and `migrate reset` do not run it.

### Dev server quirk

Under `npm run dev`, any `/api/auth/*` response with status 401 (for example a wrong password) surfaces as a 500 "fetch failed" from the Vite/Nitro dev proxy. The production build returns the 401 correctly, so verify auth error handling against a production build.

### Dates

Due dates are stored as UTC midnight. Formatting and comparison code in `dashboard-utils.ts` extracts the UTC year/month/day and rebuilds a local date so the day does not shift in negative-offset timezones. Use those helpers rather than `new Date(x).toLocaleDateString()` or direct comparisons. Anything that depends on "today" is computed in the browser at render time: the status badges (`getPaymentStatus`; `Overdue` / `Auto-Pay` / `Due Soon`, never read from the database), the stat cards (`getUpcomingStats`) and "due this week". The server runs in UTC and does not know the user's day, so keep "today" logic out of server functions.

### Deployment

`vite.config.ts` switches Nitro to the `netlify` preset when `NETLIFY` is set, and `netlify.toml` runs `prisma generate`, `tsc --noEmit` and the tests before the build, so a type error or failing test fails the deploy and the previous one stays live. Nitro bundles every dependency except the ones in `traceDeps`, which it loads from `node_modules`. `require-in-the-middle` and `import-in-the-middle` must stay in that list: Sentry patches module loading with them, and once bundled as ESM they break every later `require`, including `pg`, so the database stops working. `scripts/smoke-netlify.mjs` runs at the end of the Netlify build and fails it (keeping the previous deploy live) if the bundle cannot serve `/` or load `pg` with Sentry running; run it locally after `NETLIFY=1 npx vite build`.

`@tanstack/react-start` is held at `~1.168` because 1.169 requires Vite 8. `@tanstack/react-router` is pinned to the exact version that release depends on; a different version installs a second copy of the router. Upgrade the two together.

## Conventions

- Import with the `@/` alias (maps to `src/`), not long relative paths.
- TypeScript is strict with `noUnusedLocals`/`noUnusedParameters`; ESLint errors on floating or misused promises. Prefix intentionally unused names with `_`, and use `void` for fire-and-forget promises in handlers.
- No React Server Components and no UI component library — components are hand-built with Tailwind and `lucide-react` icons. Forms use TanStack Form.
- Tests are colocated `*.test.ts` files covering pure utilities; there is no component test setup. `vitest.config.ts` only sets up the `@/` alias, so tests don't load the app's Vite plugins.
- Commits follow Conventional Commits (`feat(scope): …`, `fix(#issue): …`).

### Styling

- Tailwind v4, configured entirely in `src/styles.css` (no `tailwind.config`). Custom keyframes and the `.reveal`/`.visible` scroll-reveal classes (driven by `src/utils/useScrollReveal.ts`) and `.feature-card` shimmer live there.
- Palette: emerald primary, teal secondary, cyan accent, gray neutrals; amber for due-soon, red/rose for overdue or errors. Gradients use the v4 `bg-linear-to-*` utilities.
- Fonts: Sora for headings, Manrope for body.
- Cards are `rounded-2xl` with soft shadows; buttons `rounded-xl`; page container `max-w-7xl mx-auto px-4 sm:px-6 lg:px-8`. `.github/copilot-instructions.md` has the full design guide with copyable class strings.
